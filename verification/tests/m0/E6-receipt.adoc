== Answer

*Yes.* On GitHub-hosted `windows-2022` and `windows-2025` runners:

* WSL2 runs the pinned rootfs;
* a VHDX bare-mounts into it as exactly one new block device, identified
  by its size and filesystem UUID;
* `e2fsck -fn` checks that device clean;
* WSL1 also runs;
* a Zig `x86_64-windows` executable cross-compiled on Linux runs.

Hypothesis H0 (hosted runners lack the virtualisation WSL2 needs) is
*refuted*. On `windows-2022`, WSL2 needed one step first: replacing the inbox
WSL with `wsl --update --web-download`. That step needed no reboot.

== Inputs

* *Fixture:* a one-off `X-CLEAN` VHDX, because E1-L has not landed. It was
  64 MiB of ext4 with filesystem UUID `75351ccf-5cb9-8193-aaac-9dac07270838`
  (ADR-008 profile C, domain `subsystem-warrior-fixture`, pending
  registration under U11). The Linux job proved it clean on the final VHDX:
  `qemu-img check` was clean, and `e2fsck -fn` on a raw image extracted from
  that VHDX returned rc 0. The image's sha256 differs on each run, because
  qemu writes random GUIDs. The probe checks it against the hash emitted by
  the job that built it.
* *Rootfs:* Ubuntu Base 24.04.5 amd64, sha256
  `e77b6f10c2590cef872b33ee9f635a0e3fd1f57fb074c0e52b5c7f56147a0c86`
  (Ubuntu's `SHA256SUMS`).
* *Tools:* these are stock-runner tools, not the Guix pin (ruling P10).
  ** `qemu-utils` `1:8.2.2+ds-0ubuntu1.18`, from Ubuntu 24.04, as shown in
     the
     https://github.com/metadatastician/subsystem-warrior/actions/runs/44207444327/job/134476926465[inputs job]'s
     apt log. It provided `qemu-img convert` and `qemu-img check`.
  ** `e2fsprogs` on the Linux runner (`mke2fs`, and `e2fsck -fn` on the
     extracted raw image) came preinstalled, so this run's log does not show
     its version. The inputs manifest recorded it, but this receipt did not
     copy it. The `e2fsck` 1.47.0 in the table above is the rootfs's copy,
     which checked the device inside WSL.
  ** Zig 0.15.2, sha256
     `02aa270f183da276e5b5920b1dac44a63f1a49e55050ebde3aecc9eb82f93239`.
  ** Later runs record every version: since the review fix, the probe copies
     the input manifests into its results.

== Consequences

The card's first answer row applies: *WSL2 and bare mount work.*

* E5, and E1-W's Windows-only scenarios (`C-HOST-COMPRESSED`,
  `R-ORPHAN-DISK`), can run on hosted runners.
* M1's end-to-end tests can run in CI.
* On `windows-2022`, each job must run `wsl --update --web-download` before
  it uses WSL2. `windows-2025` already ships a current WSL.
* The owner's cross-compilation question has a yes in its smallest form. A
  Zig executable built on Linux runs on both images.

== Limits

* This receipt covers two runner images, measured on 2026-11-17 and
  2026-11-18. Images change; the workflow stays available for re-runs
  (`workflow_dispatch`).
* The fixture is a stand-in for E1's `X-CLEAN`. E5 and M1 rerun against E1's
  real fixtures.
* The toolchain is not the Guix pin (P10). This receipt does not claim
  pinned-toolchain reproducibility.
