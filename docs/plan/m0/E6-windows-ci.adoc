== Goal

Answer, *with a workflow run*, whether GitHub-hosted Windows runners can:

. run a WSL2 distro;
. `wsl --mount <vhdx> --vhd --bare` a disk into it;
. see that disk as a block device inside the distro (`lsblk`) and run
  `e2fsck -fn` on it.

== Hypothesis, not answer

Community reports suggest standard hosted runners lack the nested
virtualisation WSL2 needs, while WSL1 works. That is *hypothesis H0*, stated
so the run can refute it. Assuming either answer without a run is this card's
falsifier.

== Method

* New workflow `.github/workflows/m0-windows-probe.yml`, `workflow_dispatch`
  plus pull requests touching it. Matrix: `windows-2022`, `windows-2025`
  (record the image versions the run reports).
* *PowerShell steps only, no third-party actions.* That keeps the evidence
  free of an action's hidden setup. If `actions/checkout` is needed, use the
  pinned SHA already in `actions.lock`. It does *not* leave `actions.lock`
  unchanged: `scripts/check-lock-sync.sh` clause 4 needs a key for every
  workflow file, including one with no `uses:` (whose value is `[]`). The
  E6 PR regenerates the lockfile with the repo's tooling
  (`gh actions-lock`, as the lock-sync gate's own message says), never by
  hand, and runs `scripts/check-lock-sync.sh` before pushing.
* Each step records a ternary verdict, `yes` / `no` / `not-run: <reason>`,
  into an I-JSON/JCS artefact:
  .. `systeminfo` / `Get-ComputerInfo` Hyper-V and virtualisation fields;
  .. `wsl --version`, `wsl --status`;
  .. `wsl --install --no-distribution` if WSL is absent (record reboot
     needs; a needed reboot is a `no` for hosted CI);
  .. import a tiny rootfs with `wsl --import … --version 2`. The rootfs is
     pinned by sha256 and fetched over HTTPS; network use in CI is outside
     W5, which binds the tool;
  .. `wsl -d <name> -- uname -a` and `wsl -d <name> -- cat /proc/version`
     (WSL2 kernel or not);
  .. capture `wsl -d <name> -- lsblk --json --bytes -o NAME,PATH,TYPE,SIZE,UUID`
     before and after `wsl --mount <X-CLEAN.vhdx> --vhd --bare`. Select a
     newly appeared disk by the before/after difference and its expected
     virtual size and filesystem UUID from the fixture metadata. Record the
     snapshots and selected device path; require exactly one matching device,
     never assume a name such as `/dev/sdc`;
  .. run `wsl -d <name> -- e2fsck -fn <verified-device>` only on that verified
     device. Two outcomes are kept apart:
     *capability `no`*: `wsl --mount` returns an error, or no new block
     device appears in the before/after difference. Record `no` for the
     bare-mount step, with the exit status, the stderr and the `lsblk` diff
     as evidence, and `no` for e2fsck, caused by the failed prerequisite.
     *`incomplete: harness`*: one or more new devices appear but none, or
     more than one, matches the expected size and filesystem UUID. That is a
     fixture or identification fault, not a statement about the runner.
     In either case e2fsck runs on no device;
  .. fallback probe: the same import with `--version 1`, to bound what *is*
     available.
* The `.vhdx` for the mount steps is `X-CLEAN` from E1 if E1 has landed;
  otherwise a one-off `qemu-img` image made in a Linux job and passed as an
  artefact. The receipt records which, plus its expected virtual size and
  filesystem UUID for device identification.
* *Cross-compilation smoke test:* a Linux job builds a trivial Zig
  `x86_64-windows` executable, and the Windows job runs it. This answers the
  smallest form of the owner's question.

== Acceptance (exit status decides)

The workflow exits 0 iff every required step, including the cross-compilation
smoke test, produced a recorded verdict of `yes` or `no` with evidence. Any
missing verdict or `not-run: <reason>` makes E6 incomplete and exits nonzero.
`no` remains a valid recorded feasibility result: "WSL2 does not work" is a
*successful* E6 outcome when all required steps have a supported verdict.
The receipt then states the answer and its consequences. A failed prerequisite
may support `no` for a dependent capability only when the receipt records that
causal evidence; an unattempted step without such evidence remains `not-run`.

*A `no` counts only after the harness has proved its own inputs.* Before any
capability step, the workflow verifies:

* the fixture's sha256: against its E1 manifest when E1-L has landed;
  otherwise against the checksum that the Linux job producing the one-off
  image emitted for it. Either way the receipt names the source of the
  expected hash. A producer's own hash only shows that the file was not
  changed in transit, so the one-off image is accepted only if the same
  Linux job also proved it is `X-CLEAN`. That means `qemu-img check` is
  clean on the final VHDX, `e2fsck -fn` is clean on a raw image extracted
  *from that final VHDX* with `qemu-img convert -O raw`, and the virtual
  size and filesystem UUID are recorded. A check of the raw image made
  before conversion does not count, because it does not cover the
  filesystem that ships. The Windows job checks those recorded results
  along with the hash. A one-off image without them is
  `incomplete: harness`;
* that the rootfs tarball's sha256 matches its pin;
* that the cross-compiled executable exists and its hash matches the Linux
  job's artefact;
* that every *static* command template parses, with its placeholders
  declared.

Commands whose arguments come from a probe result are rendered and logged
immediately before they run, not during preflight. The main case is
`e2fsck -fn <device>`, whose device is known only after the before/after
`lsblk` comparison. When the mount failed or no new device appeared, the
dependent command is not rendered at all: that is the capability `no`
described above, not a harness fault. A dynamic command whose inputs *were*
produced but cannot be rendered (an ambiguous device match, or a template
error) is `incomplete: harness` and never `no`.

If any of these fails, the result is `incomplete: harness`, which exits
nonzero, and is never a `no`. Otherwise a missing or corrupt fixture, a
broken command or a failed cross-compile would be reported as "the hosted
runner lacks the capability" without any valid probe having run.

== Falsifiers

* Concluding yes or no without a run URL in the receipt.
* A step with no recorded verdict.
* A zero exit status while any required step is `not-run`.
* Reading a step's success from its exit code alone, where `wsl.exe` is known
  to print errors in UTF-16 and may exit 0. Each step also checks its output.

== Mutations — watch it go red

* Point the mount step at a nonexistent path: the input check must classify
  it as `incomplete: harness` and the workflow must exit nonzero. It must not
  record `no`, and it must not record `yes`.
* Corrupt one byte of the fixture: the sha256 precondition must fail the run
  as `incomplete: harness` before any `wsl --mount`.
* Remove one step's verdict write: the completeness check must fail the
  workflow.
* Replace a required step's verdict with `not-run: <reason>`: the workflow
  must exit nonzero and mark E6 incomplete.

== Consequences of each answer

[cols="1,3",options="header"]
|===
| Answer | Then

| WSL2 + bare mount work
| E5 and the Windows-only fixtures run on hosted runners. M1's end-to-end
  tests can run in CI.

| WSL1 only
| E5 still runs (it needs only the registry and the filesystem). End-to-end
  WSL2 tests need another host. Options for the owner, all beyond this repo: a
  self-hosted Windows runner, a cloud VM with nested virtualisation, or a
  larger runner type if GitHub offers one with it.

| No WSL at all
| As above, and `C-HOST-COMPRESSED` must be built on an owner machine and
  committed as a signed scenario recipe.
|===

== Aspects

* *Security:* no secrets are needed, and the workflow requests read-only
  `permissions:`. The runner is disposable, so registry and WSL changes there
  are harmless and are never repeated on a developer machine.
* *Cost:* Windows minutes bill at a multiple of Linux minutes. Keep the
  matrix to two images and dispatch-only after the first answer.
* *Honesty:* both "yes" and "no" are green outcomes. Only "unknown" is red.

== As built

The E6 PR implements this card as follows. Departures are named.

* *Files:* `.github/workflows/m0-windows-probe.yml`, and under
  `tests/m0/e6/`: `one-off-fixture.sh`, `fetch-rootfs.sh`,
  `zig-smoke.sh` (with `zig-smoke/hello.zig`), `probe.ps1`, `judge.sh` and
  `judge_test.sh`.
* *Three jobs.* `inputs` (Linux) builds and checks the inputs. `probe` runs
  on `windows-2022` and `windows-2025` and records verdicts. `judge` (Linux)
  applies the acceptance rule. The completeness rule lives in the judge, a
  shell script, so `judge_test.sh` can test it offline. The test covers the
  card's dropped-verdict and `not-run` mutations, a harness fault, a verdict
  without evidence, invalid JSON, no results, and the probe's step list
  matching the judge's.
* *Toolchain (ruling P10; departure from P3).* E6 runs on stock runners:
  Ubuntu's `qemu-utils` and `e2fsprogs` packages, Zig 0.15.2 from
  ziglang.org checked against its published sha256, and the Ubuntu Base
  24.04.5 rootfs checked against Ubuntu's `SHA256SUMS`. Every version is
  recorded in the inputs and the receipt. The Guix-pinned toolchain arrives
  with the toolshed (U10).
* *Rootfs:* Ubuntu Base 24.04.5 amd64. It ships `e2fsck` (e2fsprogs 1.47.0)
  and `lsblk`, so nothing is installed inside WSL. It is gunzipped to a
  plain `.tar` on Linux, so the probe does not depend on whether
  `wsl --import` accepts gzip.
* *One-off fixture:* a 64 MiB ext4 image in a dynamic VHDX (block size
  1 MiB). The Linux job proves it `X-CLEAN` on the final VHDX: `qemu-img
  check` clean, `e2fsck -fn` clean on a raw image extracted from the
  VHDX, and the size and UUID read back. Its filesystem UUID is an ADR-008
  profile C id in the domain `subsystem-warrior-fixture`, which is not
  registered yet (U11).
* *Actions:* the Windows job runs PowerShell only. It also uses the pinned
  first-party `actions/checkout`, `actions/upload-artifact` and
  `actions/download-artifact` already in `actions.lock`. The artifact
  actions are needed to pass the inputs between jobs. The lock entry was
  added with the repo's `scripts/merge-actions-lock.rs`, because
  `gh actions-lock` is not available in the session. `check-lock-sync.sh`
  passes.
* *Inbox WSL (departure, after the first run).* `windows-2022` ships only the
  inbox `wsl.exe`. It has no `--version` and no `--install
  --no-distribution`, but it runs WSL1 distros. Presence is therefore judged
  by `--version` *or* `--status` *or* the usage text. For inbox WSL, the
  install step runs `wsl --update --web-download`, the option its own usage
  text offers, and succeeds only if `wsl --version` works afterwards with no
  reboot.
* *Device UUID (after the first run).* In the imported rootfs, `lsblk`
  returned an empty UUID, because it reads udev's database and no udev runs
  there. The probe reads each new device's UUID with `blkid -p`, which
  probes the device itself, and records both values.
* *Mutations:* `workflow_dispatch` takes a `mutation` input (`bad-path`,
  `corrupt-fixture`, `drop-verdict`, `not-run`), which runs on
  `windows-2025` only. The receipt records each run's URL.
* *Not tested locally:* `probe.ps1` and the Zig build run only in CI. This
  session has no PowerShell, and running a downloaded Zig binary was
  refused here. The `inputs` job parses `probe.ps1` with PowerShell's own
  parser before any Windows minutes are spent.
