== Goal

Generate small ext4-in-VHDX images with *exactly one declared fault each*,
reproducibly. Every later experiment is measured against these.

== Fault catalogue (`src/errors/faults.json`)

Ids are `<layer>-<name>`. Layer letters: `R` registration, `C` container,
`F` filesystem, `U` runtime, `K` config, `X` control.

[cols="2,1,4,3",options="header"]
|===
| Id | Built on | Injected fault | Expected oracle verdict

| `X-CLEAN`
| Linux
| none: the control. Departure from "exactly one fault": it declares zero
  faults, and E3's "byte-identical" check needs it.
| `qemu-img check` clean; `e2fsck -fn` clean

| `C-HDR-TORN`
| Linux
| CRC-32C of the *current* (higher-sequence) header made invalid; the other
  header is intact
| use the valid header for data; an independent header-CRC check reports
  `C-HDR-TORN`, identifying the failed copy and its expected and actual CRC.
  qemu may report clean after selecting the valid header.

| `C-HDR-TORN-BOTH`
| Linux
| both headers fail CRC-32C. Added by ruling P7 (not in the brief's list).
| qemu refuses to open the image

| `C-LOG-UNREPLAYED`
| Linux
| a valid log entry sequence, not yet applied, with the header's log GUID set
| qemu refuses a read-only open; `qemu-img check -r all` replays it

| `C-BAT-BAD`
| Linux
| one payload BAT entry points beyond end of file
| `qemu-img check` reports an error (to confirm)

| `C-HOST-COMPRESSED`
| Windows (E6)
| a clean `.vhdx` with the NTFS compression attribute set
| `compact /q` reports compressed. WSL attach fails "Access is denied" (to confirm)

| `F-SB-PRIMARY`
| Linux
| primary superblock checksum broken; backup superblocks intact
| `e2fsck -fn` reports the superblock problem, nonzero exit

| `F-HTREE`
| Linux
| one dx_root / dx_node block of an indexed directory damaged, with its other
  checksums left consistent
| `e2fsck -fn` reports an HTREE problem for that inode

| `F-FEATURE-UNKNOWN`
| Linux
| an incompat feature bit that the pinned e2fsprogs does not define. The
  superblock checksum is recomputed, so this stays one fault.
| `e2fsck -n` refuses ("unsupported feature"), exit 8

| `K-WSLCONF-BAD`
| Linux
| `/etc/wsl.conf` inside an otherwise clean ext4 carries an invalid value
  (e.g. `[boot] systemd=maybe`)
| `e2fsck -fn` clean (the fault is not a filesystem fault); the E1 test
  parses the file and finds the bad key

| `R-ORPHAN-DISK`
| Windows (E5/E6)
| a `.vhdx` on disk with no `Lxss` key referring to it. Shipped as a `.reg`
  scenario plus disk path; the E5 harness, not the probe, creates it.
| n/a on Linux; checked by E5
|===

`F-FEATURE-UNKNOWN` uses an *undefined* bit, so it is newer than any tool. On
its own it tests only "unknown bit → refuse". It does not test W3's real
case: a *known, valid* feature that is newer than the rescue tool. So M0 adds:

[cols="2,1,4,3",options="header"]
|===
| Id | Built on | Injected fault | Expected oracle verdict

| `F-FEATURE-SKEW`
| Linux
| a clean ext4 made with `orphan_file` enabled. This is a real feature, and
  e2fsprogs 1.47.0 supports it (observed 2026-10-27: `mkfs.ext4 -O orphan_file`
  and a clean `e2fsck -fn`, rc 0). It is not corrupt; it is newer than an
  older tool.
| the pinned e2fsprogs accepts it, and an *older* pinned e2fsprogs (< 1.47,
  from a second Guix channel pin used only as an oracle) refuses it
|===

*Departure from the brief:* `F-FEATURE-SKEW` is not in the brief's fixture
list. It is added because without it M0 can go green with no evidence for
the W3 version-comparison logic. Its "fault" is relative to a tool version,
so its manifest names the comparison pair (feature, minimum e2fsprogs
version, older oracle version). The first e2fsprogs version for each feature
must come from e2fsprogs' release notes and be cited, not taken from memory.

== Method

. *Toolchain.* Extend `build/manifest.scm` with `e2fsprogs`, `qemu` (or
  `qemu-minimal`, if it ships `qemu-img`), `rhash` and `zig`. Run everything
  under `guix time-machine -C build/channels.scm -- shell -m build/manifest.scm`.
  Record `guix describe` and every tool's `--version` in each manifest.
. *Payload.* `payload.json` declares a deterministic tree, written into every
  ext4 image with `mke2fs -d` and fixed mtimes:
  ** one directory with enough long-named entries to force an htree
     (`dir_index`), because `F-HTREE` needs one;
  ** files of mixed sizes (inline, single-extent, multi-extent) with
     seeded-PRNG content;
  ** at least one sparse file with more than four separate data runs, so
     its extent tree has depth ≥ 1. A contiguous multi-extent file can stay
     at depth 0. *Already observed* (2026-10-27, e2fsprogs 1.47.0, `mke2fs -d`):
     six 4 KiB runs 32 blocks apart gave depth 1, and a contiguous 3 MB file
     gave depth 0. Record each payload file's depth (`debugfs -R 'ex <path>'`)
     in the manifest. `fixtures-check` fails if no depth ≥ 1 file exists;
     E4's extent mutation depends on it;
  ** a valid `/etc/wsl.conf`.
  E2 measures recovery against this tree's sha256 list.
. *ext4 determinism.* Run `mke2fs` with fixed `-U`, `-E hash_seed=…,root_owner=0:0`
  and `E2FSPROGS_FAKE_TIME`. *Already observed* (2026-10-27, e2fsprogs 1.47.0,
  one host): two pinned runs produced byte-identical 64 MiB images, and an
  unpinned run differed. Cross-host and `-d` behaviour are not yet observed;
  step 1 of the PR establishes them.
. *VHDX.* Convert with `qemu-img convert -O vhdx -o subformat=dynamic,block_size=<explicit>`.
  Then the Zig normaliser (`tests/fixtures/wsl/gen`) rewrites every
  random GUID — FileWriteGuid, DataWriteGuid, Page83 and any other random
  field found — to a *deterministic UUIDv8* derived from (fixture id, field
  name) in the standards ADR-008 layout (owner ruling D305), and recomputes
  every checksum covering an edited byte. Read the layout from ADR-008 before
  writing the normaliser; do not use UUIDv5.
  *LogGuid is special:* [MS-VHDX] uses an all-zero LogGuid to mean "no valid
  log". The normaliser preserves a zero LogGuid. It sets a non-zero LogGuid
  only while building `C-LOG-UNREPLAYED`, together with the matching log
  entries. A non-zero LogGuid with no entries would turn every clean fixture
  into a corrupt one before any fault is injected.
. *Faults.* Apply each fault after normalisation. Recompute every checksum
  except the one the fault is about, so the image carries exactly one fault.
  For `C-HDR-TORN`, independently check both 4 KiB headers with their checksum
  fields zeroed (`rhash --crc32c`, subject to pinned-build verification).
  Record the stored (expected) and computed (actual) CRC and the failed copy;
  exactly one header must fail, while qemu's raw output uses the valid header.
  This CRC oracle is required even when `qemu-img check` reports clean.
  `C-LOG-UNREPLAYED` needs us to *write* log entries. Its independent check is
  that `qemu-img check -r all` replays them, and that the replayed raw image
  equals the intended raw image.
. *Manifests.* Write one I-JSON/JCS manifest per fixture: id, declared fault
  ids (exactly one, or zero for `X-CLEAN`), tool versions, oracle command,
  oracle exit code and a digest of the oracle's output. Linux manifests also
  record sha256 of the `.vhdx` and raw image, the Guix commit, virtual size,
  filesystem UUID, and independently recorded expected `compat`, `incompat`
  and `ro_compat` masks after fault injection (from the intact backup for
  `F-SB-PRIMARY`). Windows-only manifests record the scenario recipe and
  resulting host state instead of a reproducible image hash.

== Acceptance (exit status decides)

`just fixtures-check` exits 0 iff all of the following hold:

. For Linux-built fixtures, `just fixtures` run twice into two fresh
  directories yields the same sha256 for every generated file, *and* those
  equal the committed manifests.
. For Windows-only `C-HOST-COMPRESSED` and `R-ORPHAN-DISK`, verify the
  documented recipe and resulting state against the scenario manifest:
  respectively, a clean `.vhdx` with its NTFS compression attribute set, and
  an existing `.vhdx` with no `Lxss` key referring to its path. Record the
  Windows checks; committed image-hash comparisons do not apply.
. Every manifest names exactly one fault id (zero for `X-CLEAN`), and that id
  exists in `src/errors/faults.json`.
. For every Linux-built fixture, the oracle's verdict matches the
  catalogue's "expected oracle verdict". The verdict must match on *both*
  counts: the declared fault is reported, and nothing else is.

== Falsifiers to run (and record in the receipt)

* A fixture that `qemu-img check` / `e2fsck -n` reports as clean, other than
  `X-CLEAN`, `K-WSLCONF-BAD` and `C-HDR-TORN` (whose independent header-CRC
  oracle must still report its declared fault).
* A fixture whose oracle output reports more than the declared fault.
* Two Linux-fixture regenerations that differ in any byte.
* A Windows-only fixture whose recipe or observed state differs from its
  scenario manifest.

== Mutations — watch it go red

* Skip the normaliser once: the byte-identity check must fail.
* Inject a second fault into one fixture: the "exactly one" check must fail.
* Swap one fixture's manifest hash: the manifest comparison must fail.
* Remove the `F-FEATURE-UNKNOWN` checksum recompute: the oracle must then
  report two problems, and the test must fail.

== Risks and unknowns

* *qemu may be blind to `C-HDR-TORN`.* The independent header-CRC oracle above
  is mandatory; confirm rhash's CRC-32C support in the pinned build before
  `fixtures-check` can pass. Record which oracle judged each fixture.
* Whether qemu writes other random or time-based fields (beyond GUIDs) into
  VHDX metadata. Step 1 diffs two unnormalised conversions to find them all.
* Windows-built fixtures (`C-HOST-COMPRESSED`, `R-ORPHAN-DISK`) cannot be byte
  reproducible in the same sense. Their manifests record the scenario recipe
  and the resulting state, not a file hash.

== Aspects

* *Determinism / reproducibility:* Linux fixtures derive from the fixture id
  and the Guix pin. No clock, no randomness, no network after the Guix fetch.
  Windows-only fixtures are accepted by recipe and resulting state.
* *Independence:* the generator shares no code with the reader (LAYOUT note 2).
* *Privacy (W5):* the payload is synthetic; no real user data ever enters a
  fixture.
* *Size:* images stay small (tens of MiB, sparse), so CI regenerates them
  instead of storing them.

== Beyond this repo

A pinned fault-fixture factory is likely useful for later backends and for
`zig-vhdx` / `zig-ext4-ro`, if those become standalone packages. Keep the
generator free of WSL-specific code, except the `K-*` and `R-*` cases.
